# Gaps: packages, packs and library code

Part of the [gap register](../GAPS.md). Locations as of commit `9add179` (2026-10-07). Clusters: **L1** packages without a pack or source entry, **L2** bits-ui parts, **L3** pack exclusions, **L4** untyped package code.

## Packages without a pack or source entry (L1)

A package import is `E_DEPENDENCY` unless a mapping pack covers it or it is compiled from source (`frontend/sources.ts`: bits-ui 2.19.2 and svelte-sonner 1.2.1). A package compiled from source must declare `"sideEffects": false`; one that does not is rejected with that reason (`E_DEPENDENCY`). Exact versions only (`E_SOURCE_VERSION`, `E_PACK_VERSION`).

## Untyped package code (L4)

Package JavaScript is typed by its declaration files and by inference from its own code (`frontend/package-modules.ts`). Each inference rule covers a pattern found in bits-ui; code outside the rules meets V2 (`E_TYPE_UNSUPPORTED`) or V1. Rules added so far: field types from assignments, parameters from calls (also recursive functions, from their outside calls), empty arrays from pushes, dictionary parameters, constants of `any` literals, runed contexts from their sets, collections from their `set`/`add` calls, nullish returns, option callbacks, local listeners, and (since 2026-10-13) properties a declaration file types `any` from the values the program gives them, failing closed where a value may come from elsewhere (bits-ui's PinInput `pattern` options, [CONTRACT](../CONTRACT.md)). In package components, the default of a prop typed `any` and so typed by the values its sites pass is not lowered where every site passes the prop a value that is never undefined (since 2026-10-13): bits-ui's Checkbox `name = undefined` (checkbox.svelte:18) stopped checkbox basic, demo, description, disabled, group and invalid, which each pass every Checkbox a name; they now lower and match Chromium in the render census (case `bits-checkbox-examples`). checkbox-table still stops at that prop (`E_TYPE_UNION`): a site passes it an open value. A call through a declaration file's class counts for its implementation (since 2026-10-07: before, such calls were silently missed, which lowered bits-ui's `setState` for one of its two keys).

| Not covered | Reason | What it would take |
|---|---|---|
| Patterns no rule recognises | Each rule is pattern-specific | More rules per library, or a dynamic tier (see [the approach review](../research/APPROACH-REVIEW.md)) |
| bits-ui's `Tooltip.Provider` in a program without a tooltip (the site's layouts wrap every docs page in two): `E_TYPE_UNSUPPORTED` at `tooltip.svelte.js:16`, the trigger registry's `triggers = $state(new Map())`, whose entries only the tooltip's own code sets; with a tooltip in the program it lowers | The provider's state reaches the registry's type through its open tooltip (`TooltipRootState`, its tether) without any code that fills the map | Type an untyped `new Map()` field from the declaration file (`Map<string, TooltipTriggerRecord>`, whose `payload` is `unknown` and never read), or treat a field no reached code writes as holding nothing. The census hosts leave both providers out of examples that do not reach the tooltip ([census](../../conformance/results/shadcn-svelte-census.md)) |
| Assurance that a rule's evidence is complete | Rules decide from the calls and assignments they find; a missed site can give a wrong type silently (the `setState` case) | Rules must fail closed: unknown or unresolved sites make the type open |

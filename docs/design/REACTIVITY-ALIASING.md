# Reactivity: deep state, aliasing and staleness

Status: design of the reactivity workstream (2026-10-13), implemented in the steps below; each step records its commit and verification when it lands. It refines the deep-state model of [M3](M3-COMPONENTS.md#svelte-deep-state-ownership) and the reactivity model of [M4](M4-EFFECTS.md#reactivity-model) without changing the serialised IR (schema 5 stays). Framework facts are from the pinned runtimes: Svelte 5.57.1 for the fixtures (5.49.2 for the north star's examples; where they differ it is said), Vue 3.5.43/3.5.24, React 19.3.0, observed in Chromium 153 by the cases named here.

## The trigger

Case `symbol-context`'s first version (2026-10-13, evidence `artifacts/carousel/conformance-v1-stale/`): a provider passes its `$state` object through a context, a consumer holds it in a `const` and renders `{tone.count}`. After a click Chromium shows the new count, the native app keeps showing 0. The interim guard (`shares_mutated_proxy`, `validate.rs`, merged in `1e742eb`) rejects such constants.

**Root cause.** Natively a template binding re-evaluates when its *guard* holds: a dirty bit of a cell it reads, changed template locals, or a write of a reactive class field (`cx.rh`). A cell's dirty bit follows its tracking mode: a `proxied` cell is dirty after any write through a proxy (`owned`), an `identity` cell only when it is set to another value. A constant holding another cell's proxy is `identity`, never set, so a binding that reaches the proxy only through it never re-evaluates. The mutation itself is tracked correctly: the proxy's slots count writes, and effects and derived values, which record what they read at run time, see it. Only the static guard of template bindings ties reactivity to the *cell* through which the value was reached instead of to the *value*.

**The interpreter agrees with Chromium here, not with native:** it renders the whole tree in every flush pass, so every binding sees every change. That is the reference model's simplification of update granularity, which is sound only where re-evaluating a binding more often shows nothing new; the validator's `E_REACTIVITY` checks exist to keep programs inside that domain. The bug is that the static guard under-approximated, which neither the differential test (no fixture had the shape) nor the validator caught.

## How Svelte's reactivity works (the oracle)

From the pinned sources (`svelte/src/internal/client/proxy.js`, `reactivity/sources.js`, `runtime.js`) and the cases below:

1. **Signals** are sources (`$state` variables, the per-property sources of proxies, an array proxy's `length`, a proxy's `version` for its key set), derived values, and reactive class fields. Props are getters over the parent's expressions; plain `let`/`const` variables, class fields without runes, Maps, Sets, class instances and raw objects are not signals.
2. **Proxies** (`proxy(v)` of plain objects and arrays) are *overlays*: each property is a source created at the first access through the proxy (read, `in`, write, delete), initialised from the target at that moment; an array's `length` source is created with the proxy. Writes through the proxy set its sources and never write the target. `proxy(p)` of a proxy is `p`; a raw value stored again gets a new proxy; a nested plain value is proxied when its property's source is created, so two proxies of one raw object, and a raw object reached again through a cycle, are different proxies with independent sources.
3. **Readers** are effects (user effects, template effects, block effects) and derived values. A reader depends on the signals it read in its last run, except signals created during that run and reads inside `untrack`. It does not matter how the reader reached the proxy (a `$state` variable, a constant, a context, a prop, a class field, a Map, a closure, a function's result).
4. **Self-invalidation**: an effect that changes, during its run, a signal it read in its previous run or reads in this one runs again (`mark_reactions` marks it, `schedule_possible_effect_self_invalidation` after the run). This holds for proxy property sources as for variables.
5. **Template granularity**: each block (component fragment, `{#if}` branch, `{#each}` item, snippet) has one template effect for all its text and attribute updates; expressions containing a call are memoized as derived values passed to it (`$.template_effect(fn, [() => f(x)])`). A non-call expression is re-evaluated whenever its block's effect re-runs; a call expression only when what it read changed.
6. **Teardowns** (effect cleanups, `onDestroy`) read signals as they were before the flush: `old_values` holds the value before the first write since the last flush (5.57.1; 5.49.2 keeps the value before the *last* write), for proxy property sources as for variables.

## Decisions

**R1. Reactivity belongs to the value, not to the cell that reached it.** A proxy (Svelte) or a reactive object (Vue `ref` contents) carries its signals: per-slot write counters in `runic_js::heap` (fields; an array's length and elements). Every reader depends on the slots it reads through such an object, wherever it got the object. Tracking modes keep their meaning for the cell's *own* signal and for what a cell stores (`proxied`: overlays of plain objects and arrays; `deep`: marked reactive), and no longer decide whether reads *through* the value are dependencies.

**R2. Template bindings re-evaluate after writes to reactive heap objects they may read through.** A binding whose expression, or a function it calls (derived functions included), may read a slot of a value that may be a proxy or a reactive object adds the reactive-heap flag `cx.rh` to its guard: true in a flush pass after a write through a proxy, a reactive class field write, or (Vue) a heap mutation since the previous pass. *May be a proxy* is a type fact computed once per program (`runic_ir::reactive::ReactiveHeap`): the plain record and array types that deep state can hold (from `proxied` cells and `$state` class fields, through plain records, arrays, nullable and union types; never through class instances, maps, sets or promises, which proxies do not wrap), and, for Vue, every heap type reachable from `deep` cells. A read is a field `get` or `index` of such a type, a `for-of` over one, or a built-in given a value that can hold one. Re-evaluating a binding is unobservable where templates are pure (R7), so the guard may over-approximate; this replaces the interim guard `shares_mutated_proxy`, and costs no more than today's rule that makes every `proxied` cell dirty after any proxy write. Effects and derived values already track proxy slots at run time (M4) and keep doing so.

**R3. Proxies are overlays.** `JsRef::proxy` (and so `Own::own` for proxied cells, `$state` fields and stores into proxies) creates an object with its own storage and its own signals:
- a record overlay copies a field from its target, proxying a nested plain value, at the field's first access through the overlay (a whole read, such as a spread, `JSON.stringify` or `structuredClone`, accesses every field); writes go to the overlay only; the nested proxy counts as created with the overlay that took it, as Svelte creates a proxy's lazy sources in the reaction that created the proxy (`with_parent`), so a reaction reading a nested object first depends on it (R4; case `deep-tracking`);
- an array overlay takes its target's length and elements when it is created (Svelte's eager `length`) and proxies an element at its first access; a later in-place change of the *target* array (not through the overlay) is reported unsupported at run time (`RunicUnsupportedError`; the interpreter stops with `E_UNSUPPORTED`): Svelte would show the target's new elements at indices not yet read while keeping the old length, which a typed array cannot hold.

This gives Svelte's observable identity (a new proxy per store of a raw value and per lazy path through a cycle, the case `ownership-cycles` gap) and its ownership: the raw object stays as it was (reset values, defaults: case `proxy-target`), a raw write before the first read is visible and one after it is not (case `proxy-lazy`, and `ownership`'s write right after `push`). Vue's `deep` cells are unchanged: Vue's reactive proxies write through to their target, which in-place marking models.

**R4. Self-invalidation.** An effect that changes a signal (a cell, a reactive field slot, a proxy slot) it read in its previous or current run is due again in the next pass, for cells and heap slots alike. Before, cells re-ran only when written after the read, and heap slots never (case `effect-self`: Svelte logs `len 5 | … | len 4 | … | len 3`, native `len 5`). Cell versions come from one clock and heap writes now stamp the slots they write from another (`runic_js::heap_stamp`), so at the end of a run the effect is due again where one of its previous or new dependencies was written after the run started (`runic_runtime::self_invalidated`). Proxies the run created are not dependencies (Svelte does not track sources a reaction created). A field or element write through a proxy of a value `===` to the one the slot holds changes nothing, as Svelte's `set` of an equal value does nothing: without that, an effect that writes back what it read (`sync.mirror = sync.source`) would invalidate itself forever. Likewise, a write of a SameValue-equal value to an object deep reactive state reaches (Vue) changes nothing, as Vue's set trap (`hasChanged`) notifies nothing; before 2026-10-14 such writes re-ran a watchEffect reading the slot (case `equal-writes`). `reverse`, `sort` and `fill` set elements one by one, as the proxies' traps see them. `reverse` reads the length and every element but the middle one; `sort` reads every element; `fill` reads the length and stores the value into each element as a set does, so a proxy array takes a new proxy of a plain object at each index. Each writes only the elements that change (case `array-writes`; before, they wrote every element and `fill` stored one proxy at every index). Vue's `watchEffect` does not re-run for its own writes; the Vue adapter rejects such watchers (`E_EFFECT`), which keeps this rule framework-independent.

**R5. Teardowns read deep state as before the flush.** Where `schedule.cleanupReadsPrevious` holds (Svelte), reads through a proxy while a cleanup or `onDestroy` runs give the slot's value before the first write since the last flush, as Svelte's `old_values` do (case `teardown-proxy`: `cleanup 0/0` where native shows `0/1`, `destroy 3 3` where native shows `13 3`). An overlay keeps a before-image from its first write after a flush ended until the next flush ends, in programs whose cleanups read the values before the flush and that have proxies. A derived value a teardown reads is computed afresh from those values, neither from nor into its cache (Svelte re-executes a derived that depends on old values: `d2` where native read its cache, `d0`). The 5.49.2 rule (the value before the last write) differs for cells and slots alike; the adapter will select it by version (a schedule policy) when an example depends on it.

**R6. What a mutation notifies is decided by the mutated object.** The validator classifies each in-place mutation by the origin of the object: *through a proxy* (a `proxied` cell that is not a prop, a `$state` field, a value read from either, a constant or context whose every source is one: R8), *raw*, or *unknown*. Only raw and unknown mutations of values a template may read are rejected, as today. A `proxied` **prop** holds whatever its sites pass: raw objects included (case `prop-raw`: a child mutating a raw object through its prop is not reactive in Svelte, and Svelte shows the value when its block re-renders for another reason, which native bindings do not reproduce), so it counts as *through a proxy* only where every site passes a proxy or a value read from one (an `{#each}` item of one included), and no site leaves it to a default object (Svelte never proxies a prop's default). The same holds for Vue: a raw object stored in a deep ref and changed through another reference is not tracked (case `raw-target-vue`: Chromium shows the write at the component's next render, native and the interpreter at once), so such a change is rejected where a template reads the ref.

**R7. Templates are pure, and their reads are dependencies.** The three models (Svelte's per-block template effects with memoized calls, the interpreter's full re-render, native per-binding guards) agree exactly when every value a template expression reads changes only together with a signal the expression depends on. Besides the existing rejections (written non-reactive cells, raw mutations, host services, `lastIndex`, Date setters, maps and sets in state, dynamic values), an **untracked read** in a template (`untrack(() => …)` reached from a template expression, directly or through calls) of a value that may change is `E_REACTIVITY`: Svelte memoizes the expression and never shows the change, the interpreter shows it at the next flush and native when the untracked cell is dirty (case `untrack-template`).

**R8. Aliases of deep state.** Constants, contexts and function results whose every source is deep state are *through a proxy* (R6), so writes through them (`ctx.count += 1` of a context's `$state` object, case `alias-writes`) are accepted instead of being rejected as raw mutations. The validator follows values through `context.set`/`context.get` by key, constants never set, and the results and parameters of functions (all call sites); anything else stays *unknown*.

**R9. Frameworks keep their own models; the shared layers keep the mechanisms.** The adapters choose what a cell stores and how it is dirtied (`proxied` overlays for Svelte `$state`, `deep` marking for Vue `ref`, `identity` + `readonly` for React); the backend never branches on frameworks: R2's type fact, R3's overlays (only `proxied` stores create them), R4 and R5 are generic, gated by the program's tracking modes and schedule policies.

**R10. Vue's watcher order.** runtime-core queues the pre jobs of one instance in the order a flush triggers them (`queueJob`, `findInsertionIndex`: jobs of one id keep their queue order), and Runic runs an instance's due watchers in declaration order. Fixture `watch-order-vue` in Chromium (an expected rejection, `tests/reactivity.test.mjs`): `watch(a)` declared before `watch(b)`, both writing `status` and a log; a handler writing `b`, then `a` shows `a2` and logs `b2 | effect 2 | a2`, while the interpreter and native code show `b2` and log `a2 | b2 | effect 2`. The exact model is approved as later work: a schedule policy, a schema change ([ROADMAP](../ROADMAP.md), decisions, 2026-10-14; the [planned model](#planned-vues-queue-order-as-a-schedule-policy) below). Until it lands, the Vue adapter rejects (`E_EFFECT`, `frontend/adapters/vue-watch-order.ts`) a pair of watchers W_i declared before W_j of one component when their effects do not commute (see below) and their order is not proven.

What counts as not commuting:
- one writes state the other reads or writes;
- one mutates heap objects (plain logs included) and the other reads or mutates heap;
- both use host services (timers, microtasks, promises, storage, the DOM);
- either calls a function the analysis does not resolve.

The order is proven where, for every flush that may trigger both, three conditions hold:
- **Shared signals.** Every signal of W_j the flush may write is a ref, a prop or a record field reached through one, and W_i reads it unconditionally in every run.
- **No computed values in W_i.** W_i depends on no computed value.
- **Settled cleanups.** W_i's cleanups evaluate only settled computed values.

The flushes considered are one per handler. Each listener ends with a microtask checkpoint, so each handler's writes are flushed alone. Every flush may also contain the writes of all watchers and lifecycle hooks, of setup and template code, and Vue's own prop and template-ref updates. Function values are followed through locals, captures, parameters and props to the functions their sites pass.

Why these conditions give Vue's order:
- **Shared signals.** A ref, a prop or a record field is one signal per write: `RefImpl` triggers one dep, `updateProps` sets each key separately, and an existing key's set triggers that key. W_i subscribed to every shared signal at its creation, before W_j. Reading it in every run keeps the link: Vue drops a link a run did not read again (`cleanupDeps`), and a later read links it again at the tail. So any write that notifies W_j also notifies W_i, from the same list, where W_i comes earlier. A signal only W_i reads may be written in the same flush; that only queues W_i sooner. One batch notifies only one object's signals, and W_j depends on no array, map or iteration signals, so another signal of the batch cannot reach W_i before the shared one.
- **No computed values in W_i.** A computed's subscribers are notified at the computed's own position in the written signal's list, which is fixed when the computed gains its first subscriber, not at W_i's creation.
- **Settled cleanups.** Inside an effect's run, a computed evaluated for the first time takes over the active link of the signals it reads (`dep.activeLink`, restored to nothing after its run). W_i then links them again at the tail, behind W_j. A watchEffect's cleanup runs inside its next run. A computed value is settled when its component's template reads it unconditionally at its root, so it was evaluated at the first render, and it reads the same refs and fields in every evaluation.

Fixture `watch-cleanup-computed-vue` in Chromium (an expected rejection) shows the active-link effect. Chromium logs `cleanup 0 d2 | watch 1 | watch 2 | cleanup 1 d4 | watch 3 | cleanup 2 d6`, natively `cleanup 0 d2 | watch 1 | cleanup 1 d4 | watch 2 | …`.

**Across instances.** Vue's scheduler sorts jobs by instance uid, which is creation order. It also runs an instance's queued watchers while its parent's render patches it (`updateComponentPreRender` calls `flushPreFlushCbs`), in document order. Runic runs instances in document order. The two agree for watchers that only prop updates trigger: case `watch-instances` in Chromium, also for an item inserted at the front of a list and a branch shown before existing siblings. They differ for watchers a write triggers directly, here through a reactive object the parent passes. Fixture `watch-instances-deep-vue` in Chromium (an expected rejection): after an item is inserted at the front of the list and a branch shown before it, Chromium logs `row 1 3 | row 2 3 | row 3 3 | row 0 3`, natively `row 0 3 | row 3 3 | row 1 3 | row 2 3`.

The adapter therefore also rejects a pair of instances in one parent's template where one may be created after the other but precedes it in the document. That is a component site inside a branch, list or slot region the later site is not in, or two items of one list. The rejection applies where watchers of their subtrees have effects that do not commute and a flush may trigger both. The exception is two children of that template triggered only through their props: one render of the parent patches both, in document order. Instances further down are patched by their own parents' renders, which run by uid when they re-render for their own state. Two instances never share their own cells.

Items of one list get the same exception since 2026-10-14. Vue patches a keyed list's items in the order of its keyed diff (`patchKeyedChildren`: the common prefix forward, the common suffix backward, the rest in their previous order, with mounts and unmounts where the diff takes them), and the interpreter and native code now take the same steps (`runic_js::reorder::schedule` for the list's `reorder` strategy; case `list-order`, below). Before, native code updated a list's blocks from the last one and ran the items' watchers in reverse document order, and the interpreter used document order; the differential found it on the first `watch-instances` fixture (`row 2 1 | row 1 1`), and fixture `watch-list-vue` was an expected rejection until then (now case `watch-list`).

**List order.** Each framework creates and updates a keyed list's blocks in the order of its own keyed diff, which the list's `reorder` strategy (adapter-declared, D4) names; creating a block runs its components' setup and pre effects, updating it their due pre effects (case `list-order` in Chromium, all three frameworks):
- Svelte (`stash`): the each block creates the new items in array order (`row 5 3 | cell 5 3` before `cleanup 4 2 | row 4 3 | …` after an append), then `reconcile` moves blocks and destroys the removed ones; the flush then runs the other items' dirty effects in document order.
- Vue (`lis`): an insert at the front patches the common suffix backward, then mounts (`row 3 2 | row 2 2 | row 1 2 | row 4 2`); a reversal patches the middle in its previous order (`row 4 4 | row 1 4 | row 2 4 | row 3 4 | row 5 4`); mounts in the middle go backward (`… | row 7 6 | row 6 6`).
- React (`forward`): rendering takes the new order and runs nothing observable; layout and passive effects run in the commit in document order, as before.

The interpreter renders the blocks in these steps' order and assembles the tree in document order; generated code runs the steps, inserting each block before the first node of the nearest following block already in its final place, which keeps the DOM order whatever the steps' order.

Coverage:
- Accepted shapes, each checked in Chromium:
  - case `watch-declared`: a later watcher's signals are a subset of an earlier one's, in both write orders and through a prop's record field; two watchers no handler triggers together;
  - case `teardown-vue`: a settled computed read in a cleanup;
  - case `watch-instances`: instances triggered through their props only;
  - cases `watch-list` and `list-order`: items of one list triggered through their props, in the keyed diff's order.
- Rejected:
  - `watch-order-vue`, `watch-cleanup-computed-vue` and `watch-instances-deep-vue`;
  - `deep-tracking-vue`. This fixture has three watchEffects over deep refs logging into one array; their signals are array elements and lengths, which the analysis does not tell apart, so it moved from accepted to rejected.

### Planned: Vue's queue order as a schedule policy

The approved exact model (later work, a schema change; [ROADMAP](../ROADMAP.md), decisions, 2026-10-14) is a schedule policy, for example `watcherOrder: "triggered"`, that the Vue adapter selects. The interpreter, the runtime and codegen implement it generically. It replaces R10's rejection. Under it, a pass runs an instance's due pre effects as Vue's queue does:

- **Trigger order.** Each write is a batch: Vue's `trigger` wraps the deps one write notifies in `startBatch`/`endBatch`, and an array mutator (`push`, `pop`, `shift`, `unshift`, `splice`) wraps all of its sets. Due effects run in the order of the first batch that notified them since they last ran. An effect notified again before it runs keeps its place. A writing watcher's re-triggered successors run after the jobs already queued.
- **Ties by link order.** Within one batch, the written signals notify in the order `trigger` (`reactivity.esm-bundler.js`) visits them:
  - the key's dep;
  - `ARRAY_ITERATE_KEY` for an array index;
  - then by type: an added index notifies `length`, an added or deleted key `ITERATE_KEY` (and `MAP_KEY_ITERATE_KEY` for a map), a map's set `ITERATE_KEY`;
  - an array's `length` write instead notifies, in the order the deps were created, those of `length`, of iteration and of the indices at or above the new length;
  - `clear` notifies every dep of the collection.

  Each signal walks its subscribers from the most recently linked to the oldest (`dep.subs` is the tail, `notify` follows `prevSub`), skipping those already notified in the batch.
- **endBatch.** `batch()` prepends, so the subscriber notified last in a batch runs first. For one signal that is link order, oldest first. Across the signals of one batch, a later signal's subscribers run before an earlier signal's.
- **Links.** An effect links to a signal the first time a run reads it. A run that does not read a linked signal drops the link (`cleanupDeps`), and reading it again links it at the tail. Effects keep per-signal link stamps, renewed on a new link; heap slots need them as well as cells.
- **Computeds.** A computed subscribes to its signals while it has subscribers (`TRACKING`): it joins their lists at the tail when it gains its first subscriber and leaves them when it loses its last (`addSub`/`removeSub`). Notified, it notifies its own subscribers at once, at its position in the written signal's walk. An effect that runs because a computed was notified still checks that the computed's value changed (`isDirty`, `refreshComputed`); its place in the queue is taken when it is notified.
- **The activeLink quirk.** Within an effect's run (after `prepareDeps`), a computed evaluated for the first time, or reading a signal it did not read before, creates a new link and sets that signal's `activeLink` to it. After the computed's run, `cleanupDeps` restores the link's `prevActiveLink`, which a new link does not have. The effect's next read of that signal then makes a new link at the tail. The model reproduces this with the link stamps; the alternative is to keep rejecting it statically as R10 does.
- **Across instances.** Jobs of different instances run in `uid` (creation) order. An instance its parent's render patches runs its queued watchers then, in document order (`updateComponentPreRender`). Instances therefore need creation stamps, and the pass needs Vue's interleaving of the parent's render with its children's pre jobs (fixtures `watch-instances-vue`, `watch-instances-deep-vue`).

## What the IR expresses

No schema change. The meaning of existing constructs is made precise (docs/IR.md):
- `proxied` cells and `state` class fields store overlays (R3); `deep` cells mark what they hold reactive.
- Reads through overlays and reactive objects are dependencies of effects, derived values and template bindings, wherever the value is held (R1, R2).
- An effect run that changes what it read is due again (R4); cleanups under `cleanupReadsPrevious` read overlays' before-images (R5).

## What the validator proves

For every template expression of an accepted program: whenever the value it computes may change between two flush passes, (a) the framework re-evaluates it (the change is a write to a signal it depends on), (b) the interpreter re-evaluates it (always), and (c) native re-evaluates it (its guard holds). (c) is now structural: guards cover cells by dirty bits and reactive heap reads by `cx.rh`. The validator proves (a) by rejecting the changes that notify no signal the expression reads: written non-reactive cells, raw and unknown in-place mutations (R6), untracked reads (R7), host services, `lastIndex`, Date setters, maps and sets inside proxied state, dynamic values changed in place, plain class fields written after construction. Writes that Svelte refuses (`state_unsafe_mutation`) stay rejected as before.

## What stays rejected or reported, and why

| Pattern | Outcome | Why |
|---|---|---|
| A raw (non-proxy) object mutated in place while a template reads it, also through a `proxied` prop that may hold it | `E_REACTIVITY` | Not a signal in any framework; the frameworks show it when the block re-renders for another reason, at points native bindings do not reproduce |
| `untrack` of a changing value in a template | `E_REACTIVITY` | Svelte memoizes the expression (R7) |
| An array changed in place after a proxy over it was created, other than through the proxy | run time (`RunicUnsupportedError`) | Svelte's overlay would show new elements under the old length (R3) |
| Maps and Sets in `$state` mutated, class instances in `$state` mutated in place | `E_REACTIVITY` (unchanged) | Proxies do not wrap them |
| Teardown reads under Svelte 5.49.2's last-write rule | not modelled yet (5.57.1's rule) | Version policy, added when an example needs it |
| Two Vue watchers of one component whose effects do not commute and whose order in a flush is not proven to be declaration order | `E_EFFECT` | Vue runs them in trigger order (R10); the exact model is a planned schedule policy |
| Teardowns of removed blocks before later components' pre effects (Svelte: not detected; Vue: `rejectUnmountOrder`) | until the teardown policy lands | Runic runs them after the DOM update; the frameworks where the walk removes the block (resume list) |

The React and Vue rows (2026-10-14, [results](../../conformance/results/reactivity.md#step-7-react-and-vue-audit)), each checked in Chromium first:
- React: effects whose dependencies include the state they set (case `effect-self-react`) and state updates from cleanups at unmount (case `unmount-updates`, with a cleanup reading a ref live) agreed: regression cases. `useRef` values (and module state) mutated while rendering were already located rejections (`E_REF`, `E_REACTIVITY`), now pinned by a test.
- Vue: cleanups and unmount hooks read live values (case `teardown-vue`) agreed. Writing it found that Vue orders a component's watchers by trigger order and different instances' watchers by creation order: R10, rejected until the planned schedule policy. `deep` watchers, reactive-object sources, `reactive()`, `toRef(s)` and module refs stay located rejections with their gap rows (not lowered: see the resume list).

Remaining plan (resume here; one conformance case per row that differs, checked in Chromium first, a fix or a located rejection with a gap row for each divergence):
- Done (2026-10-14): a write of the value a Vue deep ref's slot already holds notifies nothing (case `equal-writes`); `reverse`, `sort` and `fill` read and set element by element, and `fill` stores a new proxy at each index (case `array-writes`; R4).
- Done (2026-10-14): the order of a keyed list's steps (case `list-order`, above): each framework's keyed diff creates and updates blocks in its own order, which the interpreter and generated code follow; R10's list exception is lifted (case `watch-list`).
- Next, the teardown order (found with `list-order`, 2026-10-14; schema addition approved by the user the same day): Svelte destroys a removed block where the update walk reaches it, its effect teardowns and `onDestroy` before the later components' `$effect.pre` (a removed list item after the new items are created and before the others update; an `{#if}` branch after its replacement is created); Vue unmounts a removed component where its patch reaches it (`onBeforeUnmount`, watcher cleanups), and runs `onUnmounted` in its post flush. Runic ran every teardown after the DOM update; Vue's shape is rejected (`rejectUnmountOrder`), Svelte's was silent. Plan: a schedule policy for when destroyed instances' cleanups run, the interpreter and generated code running them at the block's removal; then lift `rejectUnmountOrder` where exact.
- Then the same per-element reads and writes for `pop`, `shift`, `unshift`, `splice` and `copyWithin` (gap row in FRAMEWORKS; an effect reading an element `splice` leaves before its start runs again natively).
- Svelte, recorded gaps, ordered by what they put at risk (none is the first blocker of a census example; the first is a silent divergence):
  - raw props whose value comes from a function's result or parameter (R6: accepted today; extend `raw_capable_props` with R8's facts for results and parameters, run the census for TodoMVC-like `{#each derived as item}` sites);
  - memoized template call expressions to accept `untrack` in templates (R7);
  - the 5.49.2 teardown rule as a version policy (R5), when an example depends on it.
- Vue features still rejected, for when a north-star example needs them:
  - `reactive()` is exact as a deep cell read without `.value` (its proxy is what a deep ref holds), with nested refs rejected;
  - `toRef(obj, 'key')` and `toRefs` are refs whose `.value` reads and writes the field;
  - deep watchers need a traversal dependency, and their pairs fall under R10;
  - module refs are module state, as Svelte's `.svelte.ts` modules.

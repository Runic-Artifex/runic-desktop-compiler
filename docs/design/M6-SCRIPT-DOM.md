# M6: script DOM

Compiled programs get as much of the DOM as Chromium 153 gives scripts, so that libraries which create, move and inspect nodes (bits-ui's announcer and embla-carousel now), then plain JavaScript pages, and later Alpine.js- or HTMX-style pages can run. This is the open gap P3 ([register](../GAPS.md), [rows](../gaps/PLATFORM.md#script-dom-p3)); the user's direction of 2026-10-13 makes it a workstream of its own ([roadmap](../ROADMAP.md#decisions-log)).

The binding decisions stay as they are: no JavaScript engine by default (D7), reject or report what is not covered instead of approximating it, framework knowledge only in adapters (D10), one IR for every frontend (D1), deterministic builds. Nothing below changes ARCHITECTURE.md or bumps the IR schema. The one decision that would change a deliberate policy, run-time HTML parsing, is left to the user (below).

## What exists

The IR type `element` is already an opaque handle compared by identity, and already stands for more than elements: `runic_js::Element` reserves handles for the document, the window, the visual viewport, the body and the html element as event targets (`element.isElement`/`isDocument`). Natively it is a Blitz `NodeId`; in the interpreter a stable id of a rendered element. Script reads of framework-rendered elements are broad (layout, attributes, selectors of a subset, siblings, `closest`, `contains`, `textContent`), writes narrow (`setAttribute` checked against the framework's later writes, `appendChild` reordering a parent's own children, inline style properties). The document and the window are known by name only (`Lowerer.hostName`): the global, a parameter every call passes one of them for, a function returning one, a constant holding one. The interpreter re-renders its VNode tree from the template at every render and has no mutable DOM (T1). The harness snapshots the container and the body's content after it (`portals`); nothing before the container is observed.

## Decisions

### 1. Node values

- **One handle type.** The IR type `element` becomes the type of every DOM node and event target handle: elements (HTML and SVG), text, comment and document fragment nodes, the document, the window and the visual viewport. Its JSON spelling stays `"element"`; IR.md documents it as a node handle. A new IR type per interface (`text`, `document`, …) would multiply union, nullability and conversion rules in the validator, the interpreter and codegen for no observable gain: the static distinction already exists where it is needed, in TypeScript's types, which the language layer reads at every member access. This is an additive extension in the manner of schema 4's fragments: programs without the new built-ins are unchanged, so no schema bump (confirmed as a user decision, 2026-10-13).
- **Kinds are checked where an operation needs one.** Each built-in states the node kinds it takes. A handle of another kind gets Chromium's behaviour: the WebIDL `TypeError` (`Failed to execute 'appendChild' on 'Node': parameter 1 is not of type 'Node'.` for the window) where the member exists on the receiver's interface, and for a member the kind does not have (`text.focus()`) the `TypeError` JavaScript throws for calling `undefined`. Sound TypeScript never reaches either; they exist so that a static type that lied (an `as` cast) fails as in the browser instead of corrupting the tree.
- **The document and the window are values.** `document.node()` and `window.node()` give their handles (the existing `Element::DOCUMENT` and `Element::WINDOW`). `Document | null` is `maybe<element>`; `doc === document` is identity. Since a program can create no other document or window (no `iframe`, `DOMParser`, `document.implementation`, `window.open`; all rejected), every value TypeScript types as `Document` is the document or nullish, and every `Window` the window: a member access on such a value evaluates the receiver (with its null check) and then lowers as on the global. `hostName` stays, as a proof that lets lowering skip the receiver.
- **Type tests** (`instanceof Node`, `Element`, `HTMLElement`, `SVGElement`, `Text`, `Comment`, `DocumentFragment`, `Document`, `Window`, `nodeType`, `nodeName`) are a kind test, `node.is(n, kind)`, a pure read of the handle in both the runtime and the interpreter.
- **Identity.** A handle is the node: the same node gives the same handle for its lifetime, as long as script holds it. A node removed from the tree stays a valid detached node while a script value refers to it (Chromium keeps it alive). Natively the runtime frees removed framework subtrees at once today; script-owned nodes (decision 2) are freed only when they are detached and no longer reachable from the tree. Holding a removed *framework* node and using it is reported unsupported until the runtime gives framework nodes the same lifetime (a later slice; today `isConnected` and refs already cover the read-only cases).
- **Representation.** Natively every kind is a Blitz node (`create_element`, `create_text_node`, `create_comment_node`); a document fragment is a detached Blitz node the runtime marks as a fragment and never inserts itself (inserting it moves its children, as the DOM does). In the interpreter, script-created nodes live in an arena of their own (kind, tag, attributes, children, parent, inline style text) with ids in a range disjoint from rendered elements' ids; the body's child list there becomes explicit (the container, mounted instances, script nodes), so that body-level placement is modelled as natively.

### 2. Ownership

Every node has an owner, decided when it is created and never changed:

- **Framework-owned**: created by the runtime for a template node, an `html` fragment or an imperative mount. The framework that rendered it assumes it alone places, moves and removes it and its child list.
- **Script-owned**: created by script (`createElement`, `createTextNode`, `createComment`, `createDocumentFragment`, `cloneNode`).
- **Host-owned**: the document, `html`, `head`, `body` and the container. The runtime places mounts and the container in the body; the body's other children are free for script.

What each framework assumes about the nodes it owns, and so what script may do to them:

- **Svelte 5** places a block's content before an anchor (a comment node, or the next static node) and removes a block by walking siblings from its first node to its last, so script nodes *inside* a block's range move and disappear with the block, and script nodes outside every range stay where they are. It never re-reads a child list after creating a template.
- **React DOM** inserts a new host child before the DOM node of the next host sibling fiber, or appends it when there is none, and removes only its own nodes. A script node appended to a React-owned element therefore ends up before React's later appended children, where under Svelte it stays after them.
- **Vue 3** inserts before an anchor node it keeps (the next sibling's element, a fragment's end anchor, the `<!--v-if-->` placeholder), or appends; fragments are bracketed by empty text nodes.

Rules:

- **O1.** Script may change script-owned nodes in every way covered below, and place them in other script-owned nodes and in the body outside the container (before it, between mounts, after them).
- **O2.** Script may write attributes and inline style of framework-owned elements as today (the framework's later writes of a script-set attribute are checked against the value the element has); `className`, `classList`, `id`, `dataset`, `hidden`, ARIA reflection and `style.cssText` join `setAttribute` under the same check. Text of framework-owned text nodes is the framework's (`nodeValue`/`data` writes are reported unsupported).
- **O3.** Script changing the child list of a framework-owned element (insert, remove, replace, `textContent`/`innerText` writes) is reported unsupported at run time, except:
  - **O3a.** An element the template renders *without children* (an IR element node with `children: []`, no `html` node) is a script host: no framework ever inserts into it, so script owns its child list (O1 applies inside it). Codegen marks such elements at creation; the interpreter knows them from the template. This is the common shape of a ref'd mount point (`<div bind:this={el}></div>`).
  - **O3b.** Reordering a parent's own children (`appendChild` of a child, bits-ui's Command), as today.
  - **O3c** (the anchors slice, below). Script nodes inserted into a framework-owned element where the runtime keeps the framework's anchors and placement policy, so that later framework inserts land where the framework puts them. Until then, the existing report stands for a framework inserting into a parent whose children script reordered.
- **O4.** Script removing or moving framework-owned nodes (`remove()`, `removeChild`, `replaceWith`, inserting one elsewhere) is reported unsupported, except O3b. Script cloning a framework-owned node (`cloneNode`) is covered: the clone is script-owned.
- **O5.** Node-level traversal (`firstChild`, `lastChild`, `childNodes`, `nextSibling`, `previousSibling`, `parentNode`) is exact inside script-owned trees and at the body level. Over framework-owned child lists it is exact only where the runtime holds the nodes Chromium holds: element-level traversal (`children`, `firstElementChild`, `nextElementSibling`, `parentElement`, `childElementCount`) always is (frameworks add no elements); node-level traversal is reported unsupported where the result could be a framework anchor (a comment or an empty text node the runtime does not keep), until the anchors slice. bits-ui's `firstNonCommentChild` keeps its existing coverage.
- **Body level.** The native document's body holds the container, mounts and script nodes, and no whitespace or `<script>` elements. Conformance host pages and the census hosts write `<body><div id="root"></div><script type="module" …></script></body>`, so traversal before and up to the container agrees with Chromium; a body-level traversal that reaches past the container's last native sibling (where the page's module script stands in Chromium) is reported unsupported, and in a SvelteKit app (whose `app.html` has whitespace around the container) every body-level node traversal is.
- **Snapshots.** Content in the body before the container becomes a snapshot field, `preceding`, in the browser harness, the native probe and the interpreter, compared like `portals`. A script node inserted before the container is otherwise unobserved, which would let a wrong placement pass.

### 3. API surface, in priority order

Each entry is Chromium's behaviour for the domain stated; the rest stays rejected (`E_CALL`, `E_MEMBER`) or reported at run time.

1. **Creation**: `document.createElement(tag)` for the IR's tag allow-list (`TAGS`; a literal outside it is `E_CALL`, a computed one outside it is reported unsupported; the name is ASCII-lowercased as Chromium does for HTML documents; an invalid name throws `InvalidCharacterError`), options rejected; `createTextNode(data)`, `createComment(data)`, `createDocumentFragment()`; `createElementNS` for the SVG namespace and `SVG_TAGS` only (the SVG rules of the template apply when it is inserted).
2. **Insertion and removal** (pre-insertion validity as the DOM standard: `HierarchyRequestError` for inserting an ancestor into its descendant or a node into a text node, `NotFoundError` for a reference child of another parent; a fragment's children move in order and the fragment is left empty): `appendChild`, `insertBefore` (null reference appends), `append`/`prepend`/`before`/`after`/`replaceWith` (strings become text nodes), `replaceChildren`, `removeChild` (returns the child), `remove()` (nothing for a detached node), `replaceChild`. A removal or move of a subtree holding focus blurs it as the existing keyed moves do (`blur`, `focusout`, nested). `MutationObserver` child-list records follow every change.
3. **Text**: `textContent` (get: descendant text in tree order; set: one text node, none for the empty string; `null` is the empty string), `nodeValue`/`data` of text and comment nodes (null for elements), `innerText` set (text nodes with a `<br>` for each line break: `\r\n`, `\n` and `\r` as the HTML standard's setter does), `innerText` get reported as a layout read (it depends on rendering: `display: none` content, CSS text-transform and line breaks) and covered later through the native layout, `outerText` rejected.
4. **Attributes and reflected properties**: `setAttribute`/`getAttribute`/`removeAttribute`/`toggleAttribute(name, force?)`/`hasAttribute`/`hasAttributes`, `getAttributeNames`; `id`, `className`, `classList` (`add`, `remove`, `toggle`, `contains`, `replace`, `length`, `value`), `dataset` (camelCase to `data-` names as the HTML standard maps them), `hidden` (boolean; `until-found` reported unsupported), `tabIndex`, `title`, `lang`, `dir`; `role` and the ARIA reflection properties (`ariaLive` → `aria-live`, …, the ARIA 1.2 IDL list Chromium implements; a `null` write removes the attribute); `style.cssText` (get: the CSSOM serialisation; set: parsed through the CSSOM as `setAttribute("style", …)` is), `style.<property>` and `setProperty`/`removeProperty`/`getPropertyValue` on every element (today: inline style properties).
5. **Traversal** (O5): `parentNode`, `parentElement`, `childNodes` and `children` (live lists: their uses lower to reads at the time of each access, `length` and indexing; `[].slice.call(list)` and `Array.from(list)` copy), `firstChild`, `lastChild`, `nextSibling`, `previousSibling`, element-level counterparts, `childElementCount`, `ownerDocument`, `isConnected`, `getRootNode()` (the document, or the root of a detached tree), `hasChildNodes()`.
6. **Queries**: `querySelector(All)`, `closest`, `matches` on elements, fragments and the document; `getElementById` (script-owned connected elements included), `getElementsByTagName`/`ClassName` (live, lowered as above). Selector matching moves to Stylo's matcher (Blitz already links it), which covers what Chromium matches statically; selectors with state that Blitz does not track (`:hover` while no pointer state exists, `:visited`, `:target` outside Kit) stay reported unsupported. Until then the runic-js subset stays, with its existing reports.
7. **Comparisons**: `contains`, `compareDocumentPosition` (the bitmask, disconnected trees with Chromium's implementation-specific bit and a pointer-order tie-break reported unsupported), `isSameNode`, `isEqualNode`.
8. **Cloning**: `cloneNode(deep)`: attributes, inline style, children when deep; never listeners, control state beyond what the HTML standard's cloning steps copy (an input's value and checkedness), or framework bindings; the clone is script-owned.
9. **Document and window members**: `document.body`, `documentElement`, `head`, `activeElement` (the body when nothing is focused, as Chromium; today's `focus.current` stays for the framework-only form), `hidden` (false) and `visibilityState` (`visible`) while the window is shown (a minimised desktop window is the desktop track's: until it is modelled, the native runtime reports a visibility change unsupported instead of firing `visibilitychange`), `defaultView`, `ownerDocument`.
10. **Events**: `dispatchEvent` of `Event` and `CustomEvent` created by script with `bubbles`, `cancelable`, `composed` and, for `CustomEvent`, a typed `detail` (stored with its IR type and read back through `event.detail` at the type TypeScript gives it: a value read at another type throws `TypeError`, which only an unsound cast reaches); native event types dispatched by script run their listeners without default actions (`isTrusted` false), as in Chromium; listener options on elements, the document and the window: `capture`, `once` (also for named functions), `passive` (a `preventDefault` in a passive listener does nothing, as Chromium; Chromium's console intervention message is not an app console line), `signal` rejected until `AbortController` exists; template listeners for custom event names (Svelte's `onemblaInit`); feature tests on host objects (`'addEventListener' in node`, `typeof window.MouseEvent`) fold at build time from the host declarations.
11. **HTML strings** (decision 4): `innerHTML`/`outerHTML` get (serialisation of script-owned trees by the HTML standard's fragment serialisation; framework-owned subtrees reported unsupported where anchors differ), `innerHTML =`, `insertAdjacentHTML`, `insertAdjacentElement`, `insertAdjacentText`.
12. **Media queries, observers and frames** keep their existing timing (Chromium's update-the-rendering steps: resize, scroll, media query `change`, then animation frame callbacks with the frame's time, then style and layout, ResizeObserver deliveries with a layout after each round, IntersectionObserver updates queued as a task after the frame; MutationObserver records in a microtask after the change): `matchMedia` on window values; `MutationObserver` extended to attributes (with `attributeFilter`, `attributeOldValue`) and character data, with `MutationRecord` records (`type`, `target`, `addedNodes`, `removedNodes`, `previousSibling`, `nextSibling`, `attributeName`, `oldValue`) and `takeRecords()`; `IntersectionObserver` with an element root (its padding box clipped as Chromium's implicit-root algorithm does for the root's descendants) and `scrollMargin`; `ResizeObserver` unchanged.
13. **Layout reads** already covered (`getBoundingClientRect`, `offset*`, `client*`, `scroll*`, `getComputedStyle` of its read set) extend to script-owned nodes once connected, and `getComputedStyle` gains the margin and padding longhands in pixels (embla's `margin-right`; percentage values resolved against the containing block as Chromium resolves them for `getComputedStyle`, which is the used value for margins and paddings).

### 4. HTML strings

ARCHITECTURE's deliberate policy says "No run-time HTML parsing". Within it:

- **Build-time strings.** `innerHTML =` and `insertAdjacentHTML` with a value from a finite set of strings known at build time (literals, constants, conditionals over them; the same rule as `{@html}`) lower to the IR's `html` fragments (`Program.fragments`), parsed at build time by the fragment-parsing algorithm with the receiver's tag as the context element; a value outside the set at run time is reported unsupported, as `{@html}`'s is. Fragment elements are script-owned when inserted by script. `<script>` elements in a fragment are inert (Chromium marks them already started; they never run); event handler content attributes (`onclick="…"`) are JavaScript and are rejected at build time.
- **Run-time strings** (`` el.innerHTML = `<li>${name}</li>` ``, the common plain-JavaScript idiom, and every HTMX swap) need run-time parsing. User decision (2026-10-13): yes, as an opt-in capability, planned as a later slice (default builds unchanged). A `"htmlParsing": true` capability links Blitz's html5ever fragment parser into the runtime; the fragment-parsing algorithm runs with the receiver as context; elements outside `TAGS`, `on*` attributes and `javascript:` URLs found at run time are reported unsupported (they would need a JavaScript engine or behaviour the runtime does not have); `<script>` elements stay inert, exactly as in Chromium; no sanitizer is applied (Chromium's `innerHTML` sanitises nothing; `setHTML` and the Sanitizer API are separate and rejected). It changes the deliberate policy for programs that opt in only, which pay its binary size.

### 5. Layers

- **Language layer** (`frontend/language.ts`, shared by every frontend): lowering of every API above from TypeScript's types, the document and window as values, kind tests, live-list reads, listener options, `CustomEvent` details. Host declarations (`frontend/dom.d.ts`) gain the interfaces (`Node`, `Text`, `Comment`, `DocumentFragment`, `NodeList`, `HTMLCollection`, `DOMTokenList`, `DOMStringMap`, `MutationRecord`) with exactly the covered members, so that anything else is a TypeScript error at the use, which the frontend reports as `E_MEMBER`.
- **Adapters** keep only what is framework-specific: template-owned nodes (they already emit them), O3a's childless elements (implicit in their templates), and in the anchors slice each framework's placement and removal policy as IR data, never as a framework name in the backend (D10).
- **IR** (`runic-ir`): the new built-ins with type rules, the snapshot field; no new types, statements or template node kinds before the anchors slice.
- **Interpreter**: script-owned nodes, the body's child list and every operation on them, so that the differential covers them; operations on framework-owned child lists and on layout stay `RunicLayoutError` (reported incomplete, never passed).
- **Runtime** (`runic-runtime`): ownership records (script-owned nodes, script hosts), every operation over Blitz's mutator, the run-time reports, MutationObserver records.
- **Codegen**: the built-ins' Rust spellings, script-host marks on childless elements.

## Plain-JavaScript frontend

The end-to-end proof, once slices 1–4 have landed: a frontend for a page made of an `index.html` and module scripts, with no framework.

- **Collection.** The collector parses `index.html` at build time; the body's markup inside the container (`<div id="root">…</div>`, the harness convention) becomes creation code: each node is created by script-owned operations at start, before the module scripts run, in document order, as the HTML parser creates them; attributes are literal. Inline `<script>` and `on*` attributes are rejected; module scripts (`type="module"`, local `src`) run in document order after parsing, as deferred modules do, then `DOMContentLoaded` (document, bubbling to the window) and `load` fire as tasks.
- **Lowering.** The module scripts go through the shared language layer unchanged: there is no reactivity, so the IR program has one component with no cells, an empty template (the container is then a script host by O3a) and an effect-free mount that runs the generated start function. Every node is script-owned, so O1 covers everything the page does.
- **Scope.** Static types come from TypeScript's inference over the JavaScript (D16); untyped values are rejected or, with `"dynamicValues": true`, dynamic. Run-time HTML strings wait for decision 4.
- **Proof.** A TodoMVC written in plain JavaScript (createElement, listeners, `classList`, `localStorage`), against Chromium with interaction.

## Analysis: Alpine.js and HTMX (not planned work yet)

- **Alpine.js** evaluates attribute expressions (`x-data`, `x-show`, `x-on`, `x-bind`, `x-text`, `x-model`, `x-for`, `x-if`, `x-effect`, magics such as `$el`, `$refs`, `$dispatch`, `$nextTick`) with `new Function` at run time, over `@vue/reactivity` proxies, and initialises nodes it finds through a MutationObserver. Compiling Alpine's source is impossible without an engine. Compiling an Alpine *page* is an adapter, like Vue's: parse `index.html` at build time, compile each attribute expression as JavaScript in the scope of its `x-data` object (typed by inference over the object literal), lower `x-data` to component cells, `x-bind`/`x-text`/`x-show`/`x-on` to template holes and listeners, `x-for`/`x-if` over `<template>` content to `each`/`if` nodes, `x-model` to the existing control bindings, and Alpine's scheduler (effects queued as microtasks, `$nextTick`) to D4 policies. It additionally needs: `<template>` content, Alpine's exact effect order verified against Alpine in Chromium, `x-transition`'s class timing (CSS transitions exist), `Alpine.data`/`Alpine.store` registrations in module scripts, and rejecting what cannot be compiled: expressions built or injected at run time (attributes added by script, `x-html` and server-rendered fragments carrying `x-*` attributes, which need decision 4 and still could not be compiled), `Alpine.evaluate` of strings, plugins without a pack.
- **HTMX** is attribute-driven network I/O: `hx-get`/`hx-post` requests, swaps of the response HTML into the page (`innerHTML`, `outerHTML`, `beforeend`, out-of-band swaps), `hx-trigger` event specifications, history snapshots (cached `innerHTML`), and `hx-on`/inline scripts in responses. It needs: run-time HTML parsing (decision 4), a network host service with an origin (P5 `fetch`, M8's embedding decides where a desktop app's server is: a local server, or the Runic bridge serving HTML), processing of `hx-*` attributes on swapped-in content at run time (a native implementation of htmx's attribute semantics in Rust, validated against htmx in Chromium as a mapping pack is, D9), and rejecting response scripts and `hx-on` code (JavaScript at run time). It belongs after M8.

## Slices

Each slice: frontend lowering, IR built-ins, validator rules, interpreter (or an honest unsupported in the differential), codegen, runtime, node tests, a conformance case against Chromium with interaction passing every gate at both viewports, CONTRACT/IR/gap rows updated. Ordered by what they unblock.

3. **Events.** Listener options, `Event`/`CustomEvent` with `detail`, native types dispatched by script, template listeners for custom names, host feature tests (done 2026-10-14, outcome below).
4. **embla-carousel.** Svelte's `use:` (in the Svelte adapter, F1), embla compiled from what npm installs (user decision 2026-10-14: the untyped ESM bundle, typed through the package's shipped `.d.ts` files by extended package-typing rules; no pinned fetch of its TypeScript sources, no new dependency), live `children` lists, IntersectionObserver element roots, MutationObserver records (child lists, then attributes), `compareDocumentPosition`, `getComputedStyle` margins, `visibilitychange`. Cases: shadcn-svelte's carousel examples with clicks on the buttons and keyboard.
5. **Selectors** through Stylo.
6. **Anchors** (O3c): each framework's placement and removal policy as adapter-declared IR data, comment and text anchors kept natively, node-level traversal over framework-owned lists; cases per framework (Svelte, React, Vue) with script nodes inserted into elements the framework later updates.
7. **Build-time HTML strings** (decision 4, first part).
8. **Plain-JavaScript frontend** and its TodoMVC.
9. **Run-time HTML parsing** behind `"htmlParsing": true` (user decision 2026-10-13); then Alpine (an adapter) and HTMX (after M8).

## Slice 1 outcome (2026-10-13)

Implemented as decided above, with these refinements:

- **Document values.** `hostName` also proves a name (or a member chain) TypeScript types as the document or the window, not nullable; elsewhere a value of either type is a nullable node handle (`document.node`, `window.node`). A document member read on a node value the program does not know to be the document (untyped package code, where TypeScript sees `any`) checks at run time that it is (`element.isDocument`): `createElement` on another node throws the `TypeError` JavaScript throws, `body` (undefined on another node) is reported. `element.querySelector` of the document handle searches the document.
- **Creatable tags** are the static elements (`{@html}` fragment tags, the inert text-level and table elements); script hosts exclude controls, void elements, table sections and SVG.
- **Text nodes** are created by `textContent`/`innerText` but are not handed out as values yet: a `firstChild` that is one is reported (slice 2).
- **`style.cssText`** reports a declaration the style engine does not parse instead of serializing without it.
- **The interpreter** models script-owned nodes and the child lists script owns (an arena, regrafted into the rendered tree after each change), so the differential is complete for the case; the body's script content after the container is not modelled there (natively it is).
- **Consumer typing.** bits-ui's announcer is untyped JavaScript with a declaration file; two package-typing rules (functions returned as declared members, and local arrows called only through such members) and svelte-toolbelt's `srOnlyStylesString` were added so that it lowers. The calendar examples now stop at `instanceof` of an untyped value in bits-ui's date-time utils (utils.js:115), outside the script DOM.
- **Verification.** Case `script-dom-announcer` passes semantics, geometry and pixels at both viewports (also `--no-opt`); the differential compares 520 steps without failure; the IR of every other conformance fixture is unchanged. Census: 280 of 404 lowered, as before; 22 rejected examples moved past their first blocker (14 calendars and date pickers, 6 carousels, 2 hover cards; [results](../../conformance/results/script-dom.md)).

## The dispatch path (for new event kinds)

Other workstreams add event kinds (CSS slice 3b: animation and transition events). The path an event takes, and what a new kind needs from it:

- **Kinds.** An IR event kind is an entry of `EVENT_KINDS` (frontend/ir.ts) and of `runic_js::Event`. Whether a listener of a type hears native events is `runic_js::event::listening(target kind, type)`, shared by the frontend, the validator, the runtime and the interpreter: a type in `FIRED_TYPES` is delivered (`Fired`); a native type outside it is rejected as a literal and reported at run time (`Unsupported`); `NEVER_FIRED_TYPES` and custom types reach only script dispatches (`Script`). A kind the runtime starts to fire moves into `FIRED_TYPES`; where it reaches (an element's path, the document, the window) is the `match` that follows.
- **Paths.** The runtime builds the path from the target to the root (the document and the window included where the DOM standard says), runs capture listeners top-down, then the target, then the bubbling phase per node through `Listeners::bubble_stage` (runtime dom.rs), which every dispatch uses: native input, nested dispatch and `dispatchEvent`. Non-bubbling kinds stop at the target.
- **Framework order.** Where an adapter declares `schedule.delegation` (Svelte: the IR kinds among Svelte 5's `DELEGATED_EVENTS`), `bubble_stage` runs that framework's template listeners of those kinds as one callback when the event reaches a delegation root (the container, or a component mounted into the body) or a listener of the framework's own (`element.listen`, svelte/events' `on()`). A new kind outside that list is delivered at its element, which is exact for Svelte (animation and transition events are not among `DELEGATED_EVENTS`). Where an adapter declares `schedule.elementListeners` (Vue), template listeners are their elements' own native listeners in registration order, which is how the runtime's listener lists hold them, so no order is reported. Where an adapter declares `schedule.rootDispatch` (React 19), the container holds the framework's root in both phases: `Listeners::capture_stage` runs the template's capture listeners of the kind from the root down when the event reaches the root's capture listener, and `bubble_stage` the others from the target up at its bubbling listener, each with `Event::enter_root` (a stop flag of the framework's event). A new kind React delegates (animation and transition events) needs only its entry in `rootDispatch.kinds` in the React adapter once it is in `EVENT_KINDS`. Where none is declared (no frontend today), `Listeners::order_conflict` reports an order that may differ, for the events the runtime dispatches (events.rs) and for nested dispatches (`run_nested_inner`, through `check_listener_order`), and the interpreter's `check_listener_order` at the same points.
- **Template listeners** of a kind lower to the element's `listeners`; listeners script adds to `target.listen`; custom types to `customListeners`.

## Next: React's and Vue's dispatch as their own policies

ARCHITECTURE D4 (user principle, 2026-10-14): each framework behaves exactly as in the browser, its differences replicated as its own adapter-declared policy, never merged into a shared approximation; a located rejection is only a stopgap. React's `E_EVENT` where a listener script adds meets React handlers of its kind, and Vue's over-reporting run-time report, are such stopgaps. Order (coordinator asked, 2026-10-14): these two policies come first, then embla; Vue's was done on the delegation branch itself (outcome above), React's follows after its merge. They reuse the code path `schedule.delegation` introduced, and they remove a stopgap from every React and Vue program where embla serves one library.

- **React** (react-dom 17 and later): `createRoot` listens on the container for every event React supports, once in the capture phase and once in the bubble phase; at the root's capture listener React runs every `on…Capture` handler along the fiber path, and at its bubble listener every `on…` handler, as one callback each. Script listeners below the root therefore run after all React capture handlers and before all React bubble handlers; a native `stopPropagation` below the root keeps React's bubble handlers from running, and React's `e.stopPropagation()` stops the native event at the root. Events React does not delegate (`scroll`, media events, `cancel`/`close`, …: `nonDelegatedEvents`) are listened at their elements; React's own mappings (`onMouseEnter` from `mouseout`/`mouseover`, `onFocus` from `focusin`, `onChange` from `input`/`change`/`click`) stay as the adapter lowers them today. IR: a separate `schedule` field of its own (for example `schedule.rootDispatch`: the kinds React runs from the container in both phases), leaving `schedule.delegation` as it is; the field is put to the coordinator before it is implemented, since `schedule` is shared with the reactivity workstream.
- **Vue 3** (done 2026-10-14, before the delegation branch's merge: `schedule.elementListeners`, case `element-listeners-vue`, outcome below): template listeners are native listeners Vue adds at their elements (one invoker per event name, created when the element is created, before it is inserted and before `onMounted`; a re-render swaps the invoker's value in place, keeping its position); `.capture`, `.once` and `.passive` are listener options. The invoker ignores an event whose `timeStamp` is earlier than the time it was attached. So the exact model is registration order at the element, which the runtime's listener lists already hold: Vue's policy declares that template listeners are registered at creation, and the run-time report goes.
- **Verification**: a case per framework with script listeners (capture, bubble, stopPropagation in each) next to template handlers of the same kind, against Chromium, and a re-screen of every React and Vue case.

## React's root dispatch (2026-10-14)

Measured with React 19.3.0 in Chromium 153 (probe app with script listeners at the window, the document, the container before and after `createRoot`, elements in both phases, and React handlers of both phases):

- `createRoot(container)` adds one capture and one bubbling listener at the container for every event, before the first render; React 19 adds nothing at the document or the window. At the capture listener React runs every `onXCapture` handler on the fiber path, root down (`eventPhase` 1), at the bubbling listener every `onX`, target up (`eventPhase` 3, also at the target), each as one callback; `nativeEvent.currentTarget` is the container.
- A synthetic `stopPropagation` ends the rest of that synthetic event's handlers and stops the native event: the container's invocation finishes (listeners added there after `createRoot` still run), later invocations do not. A native stop below the root keeps the bubbling group from running; a native stop at the container before React's listener does not skip React's group (the synthetic event's flag starts clear).
- A checkbox's or radio button's `onChange` runs in the click's bubbling group after all `onClick` handlers, as a separate synthetic event: an `onClick` stop does not skip it. The native `input` and `change` events follow the click and reach only script listeners. React decides by its value tracker: a render between the toggle and the group re-applies the controlled `checked` and onChange does not run (case `root-dispatch-react`'s first version showed it).
- Text inputs' `onChange` comes from the `input` event's group; `onSubmit` from the submit event's; `onFocus`/`onBlur` from `focusin`/`focusout`; `onScroll` (nonDelegatedEvents) is the element's own listener, `onScrollCapture` from the root. `onMouseEnter`/`onMouseLeave` come from `mouseout` (or `mouseover` when the related node is outside React) at the root, before the native over listeners.
- React skips `onClick`, `onDoubleClick`, `onMouseDown`, `onMouseMove`, `onMouseUp` (and capture forms) on a disabled button, input, select or textarea; Chromium still dispatches `pointerdown` to a disabled button. Nested `click()` and `dispatchEvent` from a handler are dispatched fully and synchronously.
- Animation and transition events are delegated like click (`onAnimationEndCapture` from the root's capture listener).

Implemented (coordinator approval 2026-10-14, one schedule field): `schedule.rootDispatch` `{ kinds, skipDisabled, reported }` (IR.md "Delegation"), exclusive with `delegation` and `elementListeners` (validator test), read with the existing `schedule.changeWithClick`; element listeners gain `capture: true` (React's `onXCapture` as element props of the root's kinds). The React adapter states the model as React 19's (`ROOT_KINDS`, `SKIP_DISABLED`), so another React version changes only the adapter. The stopgap `E_EVENT` for listeners script adds next to React handlers, the mixed native submit rejection and the run-time order report for React are gone; `onMouseMove` on disabled controls is covered.

Stopgaps that remain (PLATFORM P3 rows): listeners script adds for over or out events next to React enter or leave handlers of that family (`E_EVENT`, `rootDispatch.reported` at run time); a render during a controlled control's input event before its onChange runs, and `dispatchEvent` of an `input` event reaching an onChange (run time); capture handlers in rest props and of `onChange`, `onScroll`, enter and leave (`E_EVENT`).

Verification: cases `root-dispatch-react` (19 actions over capture and bubble groups, native and synthetic stops in both phases, the checkbox's onChange, onSubmit after a native submit listener, nested `click()` and `dispatchEvent`, a script click at a disabled button), `nested-order-react` (new case for the fixture: requestSubmit and dispatchEvent from handlers) and `capture-stop-react`, then every React case.

## Svelte's fragment order, for `schedule.bindingsLast` (2026-10-14)

Handed to the reactivity workstream (coordinator decision 2026-10-14: the exact model is theirs, on top of their pending list-order and teardown work; until then a run-time report, below).

- **The fragment model** (Svelte 5.57.1's client output, `$.action`, `Batch.#traverse`). A component's template, a block's content and a snippet's body are each compiled as one fragment: its init code creates, in template order, the render effects of its blocks (`$.if`, `$.each`, `$.key`, `$.html`, `$.snippet` for `{@render}`, `<svelte:element>`), its child components' branches and its spreads' `$.attribute_effect`, and `$.action(node, …)` after the element's content; then one `$.template_effect` holding all of the fragment's text, attribute, `value`, `class:` and `style:` bindings, created last (only `bind:` effects follow it). Effects form a tree in creation order and every flush walks it in pre-order, running dirty render effects on the way (user effects are collected and run after). An action is a user effect (`effect`), and its `update` a `render_effect` created in its first run, so a child of the action's effect: in a flush it runs after the render effects of everything created before the action (the blocks and components before it and inside its element, with their own merged bindings and the `$effect.pre`s of those components), and before its own fragment's merged bindings and the merged bindings of every fragment enclosing its component (the parent's `template_effect` comes after the child's branch).
- **The IR's order.** An instance runs its pre effects when the template update reaches it, then its template in document order, bindings and child instances interleaved; an action's update is a child pre effect of the action's effect, so it runs before the instance's template. Natively (`update_s`) bindings are written as the walk passes them; the interpreter renders a new tree and commits it at the end, so its DOM reads during a render see the tree before the flush.
- **Measurement** (Chromium 153, scratch probe: App `<p id="parent-before">{count}</p><Ord {count}/><p id="parent-after">{count}</p>`; Ord `<div use:act={count}><Kid {count}/><span id="own">{count}</span>{#if count >= 0}<i id="blk">{count}</i>{/if}</div>`, Kid `<b id="kid">{count}</b>` with an `$effect.pre` logging; `update` logs the five texts). After `count` 0 → 1: Chromium `parent-before 0, kid 1, own 0, blk 1, parent-after 0`, and Kid's `$effect.pre` before `update`; the interpreter `0, 0, 0, 0, 0`. So (a) the blocks and components before the action differ in both engines (Svelte has run them), (b) bindings of enclosing fragments before the component differ natively only (written before `update` by the walk; old in Svelte and the interpreter), so natively and in the interpreter (b) also disagree with each other; the component's own bindings (`own`) and those after it agree everywhere (old). State interplay follows the same order: a child's `$effect.pre` that writes state the update's value reads runs before it in Svelte and after it in the IR (another pass, another `update` call).
- **The model to build** (`schedule.bindingsLast`, adapter-declared): in each fragment, blocks, child instances, spreads and actions' update effects update in template order, then the fragment's bindings; an action's update runs at its action's position in that walk instead of in the instance's pre phase; the interpreter's DOM reads during a render see the writes made so far. It changes the order of bindings against child pre effects for every Svelte program (observable only through DOM reads or state writes in pre effects and updates), so every Svelte case is re-screened.
- **Until then** (`effect.after-content(before, enclosed)`, IR.md): Svelte's action update calls it before `update`. `before` (adapter, from the AST) says whether Svelte creates render effects before the action in its component (blocks, components, spreads up to the element's end); `enclosed` (adapter, over the IR of the program, a least fixed point over component sites, slot content and slot nodes) whether an instance may be rendered after a binding of an enclosing fragment. Both engines report the update unsupported where, in the same flush pass, `before` holds and the instance or a descendant is updated, or `enclosed` holds and its parent is, or the heap was mutated (bindings and effects that read deep state run again whatever instance updated). Case `actions-update` reads the component's own text in `update` (old in Chromium and both engines, not reported); `tests/actions.test.mjs` checks the report and its flags.

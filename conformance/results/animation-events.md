# Animation and transition events (2026-10-14)

CSS compatibility slice 3b, part 1: `animationstart`, `animationiteration`, `animationend`, `animationcancel`, `transitionrun`, `transitionstart`, `transitionend` and `transitioncancel`, with `elapsedTime`, `animationName`/`propertyName` and `pseudoElement`, dispatched with Chromium 153's timing; and the frame order of HTML's "update the rendering" (the `finished` promises, then animation events, then animation frame callbacks) natively and in the probe's virtual time.

Chromium 153.0.8010.12, CPU renderer. Forks (signed, not pushed): Blitz branch `animation-events` (`c3b5cfed`, `f13345e7`, `a299b0b5`, `767545c0` on `runic` `f2e6b1ad`), Stylo branch `animation-events` (`fa4e9652` on `runic` `c7f58a4e`).

## Chromium (measured on scratch pages, real time)

The event rules are Blink's `CSSAnimations::AnimationEventDelegate` and `TransitionEventDelegate`, applied to each frame's sample ([design](../../docs/design/M6-LIBRARIES.md#animations) has the full list). Measured, among 50 scenarios:

- **Frame order.** Within a frame: the `finished` reactions, then the events (each listener a callback with its microtask checkpoint), then the animation frame callbacks, including those a `finished` reaction and an event listener request (they run in the same frame); tasks the listeners queue run after the frame.
- **Timing.** A start when the animation enters the active (or after) phase; one `animationiteration` per frame however many iterations passed (5 ms iterations at 16.7 ms frames: `elapsedTime` 0.03, 0.05, 0.065, 0.08, the current iteration's boundary); a negative delay past the end starts and ends at once (`elapsedTime` the active duration, 0.2); zero-duration animations start and end in one frame; a paused animation fires `animationstart`.
- **Cancellations** are queued at the style update that makes them (also a forced one: `getComputedStyle` in a task, or in another animation's `animationend` listener) and dispatched with the next frame's events, before them; `elapsedTime` is the animation's current time (delay included: 0.05 for one cancelled 50 ms into a 100 ms delay) or a transition's active time (0 in its delay); none for an animation created and cancelled before a frame, or cancelled after its end; a removed element's own listeners receive it, the document's do not.
- **Order** within a frame: transitions before animations; elements by address (two elements created in the reverse of tree order fire in creation order); an element before its `::before` and `::after`, then its children; an element's animations in `animation-name` order; transitions ending together by property name (`height`, `opacity`, `translate`, `width`); the `transitionrun`/`transitionstart` of transitions started in one style change in neither declaration nor name order (a hash table).
- **Events**: `AnimationEvent`/`TransitionEvent`, `bubbles` and `cancelable` true, `composed` false, at the originating element (`pseudoElement` `::before`); a reversed transition is cancelled (its active time) and a new one starts, ending after the shortened duration (0.05).
- **React 19.3**: the root dispatches `onAnimation*`/`onTransition*` at default priority (React's capture handler before the target's own native listener, the bubble handlers after it, the state update rendered after the frame); `transitionrun`, `transitionstart` and `transitioncancel` carry a plain `SyntheticEvent` without `propertyName`/`elapsedTime`/`pseudoElement`; no `onAnimationCancel`.

## Under the harness

The harness stops the document timeline and seeks animations to virtual time. Measured: after a seek Chromium dispatches the events at its next rendering frame with the sought phases (the same rules, `elapsedTime` from the virtual time). The harness now (when the program may listen to these events) awaits one rendering frame after every seek (a fresh `ResizeObserver`'s first notification), and runs each 16 ms frame *F* of a `wait` as: the timers due by *F* − 1, the seek to *F* (the `finished` reactions and events, clock *F* − 1), the timers due at *F* (the frame's callbacks, also those requested in the events), another seek. Before, the frame's callbacks ran before its seek, so a callback requested in an `animationend` listener ran a frame later than in Chromium.

## Implementation

- Blitz fork: records every animation (start, delay, duration, iterations, paused local time) after each style traversal and samples them with Blink's rules at the embedder's frame (`take_animation_events`), times in whole microseconds; cancels animations under a `display: none` ancestor (Chromium does; Stylo kept them running and continued them when shown again); `Document::update_rendering` for the embedder's frame steps before the shell renders. Stylo fork: animation times compared in whole microseconds (`finished` at an end that falls exactly on a frame came a frame late).
- IR (additive within schema 5): the eight event kinds; event members `elapsedTime`, `animationName`, `propertyName`, `pseudoElement` (`AnimationEvent`, `TransitionEvent`).
- Runtime: `animation_events` (dispatch through the shared path after the `finished` settlement: `Handler::fire` with `Listeners::capture_deliveries` and `bubble_stage`, the kinds in `runic_js::event::FIRED_TYPES`, since the rebase on main f5919bb); the animation step samples after its resolution; natively the shell's redraw is the frame (`update_rendering`: the animation step, then the animation frame callbacks, which no longer run on 16 ms clock boundaries in apps); the probe's `wait` frames in the order above.
- Adapters: Svelte (element attributes, `<svelte:document>`), Vue (`@animationend`, …) and `addEventListener`; React's props rejected (`E_EVENT`) until its root dispatch is modelled.
